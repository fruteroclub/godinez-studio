# Migration Guide — Godinez Studio

## Context

Godinez Studio uses **Drizzle ORM** + **drizzle-kit** to manage the PostgreSQL schema. The schema is defined in TypeScript in `packages/db/src/schema/` and drizzle-kit generates SQL migration files in `apps/api/drizzle/`.

## Key Concepts

### What is a migration?

A versioned SQL file that describes an incremental change to the database structure — creating tables, adding columns, modifying types, creating indexes, etc. Each migration is a step that is applied in sequential order.

### Why not edit the DB directly?

- There's no record of what changed or when
- The change can't be replicated across environments (dev, staging, prod)
- There's no controlled way to revert
- The team can't review the change before it's applied

## Database Architecture

```
packages/db/src/schema/     ← TypeScript schema (source of truth)
apps/api/drizzle/           ← SQL files generated by drizzle-kit
apps/api/drizzle.config.ts  ← drizzle-kit configuration
```

## Commands

All commands are run from `apps/api/`:

| Command | What it does | When to use it |
|---------|--------------|----------------|
| `pnpm db:generate` | Compares TS schema vs last snapshot → generates `.sql` file | After modifying any file in `packages/db/src/schema/` |
| `pnpm db:push` | Applies the schema directly to the DB (no migration file) | **Local development only** — never in production |
| `pnpm db:studio` | Opens a web GUI to explore the DB | To inspect data during development |

> **Note:** Commands read `DATABASE_URL` from `apps/api/.env.local`. If you don't have that file configured, the commands will fail.

## Workflow for PRs that include schema changes

### Step 1 — Modify the TypeScript schema

Edit the files in `packages/db/src/schema/`. Example: adding a column.

```typescript
// packages/db/src/schema/users.ts
export const users = pgTable("users", {
  // ... existing columns
  phone: varchar("phone", { length: 20 }), // ← new column
});
```

### Step 2 — Generate the SQL migration

```bash
cd apps/api
pnpm db:generate
```

This creates a new file in `apps/api/drizzle/`, for example `0001_add_user_phone.sql`:

```sql
ALTER TABLE "users" ADD COLUMN "phone" varchar(20);
```

### Step 3 — Review the generated SQL

Open the file and verify that:
- It only does what you expect (doesn't drop tables/columns by accident)
- The data types are correct
- The constraints and foreign keys are correct

### Step 4 — Include both changes in your PR

Your PR must include:
- The TypeScript schema changes (`packages/db/src/schema/`)
- The generated SQL file (`apps/api/drizzle/`)

**If your PR changes the schema but doesn't include the SQL file → it won't be approved.**

### Step 5 — Apply the migration to the development DB

> **Contact Mel to get the development `DATABASE_URL`.**
>
> Mel manages database credentials in Railway. Before applying any migration you need to:
>
> 1. Ask **Mel (@melAO)** for the connection URL of the target environment
> 2. Mel shares it through a secure channel (DM, not in public channels)
> 3. Configure your `apps/api/.env.local` with that URL
> 4. Apply with `pnpm db:push` (for now, until we have `db:migrate`)

```bash
# In apps/api/.env.local
DATABASE_URL=postgresql://user:password@host:port/dbname
```

```bash
cd apps/api
pnpm db:push
```

### Step 6 — Verify

Open Drizzle Studio to confirm the changes were applied:

```bash
cd apps/api
pnpm db:studio
```

## Rules

1. **Never run `db:push` in production** — it's destructive, it can delete data
2. **Never share `DATABASE_URL` in public channels** — always via DM
3. **Never commit `.env` files** — they're in `.gitignore`
4. **Always review the generated SQL** before including it in the PR
5. **One PR = one schema change** — don't mix migrations from different features
6. **If the generated SQL drops something unexpected** — check your schema, you probably deleted something by accident

## Migration code review checklist

- [ ] Does the SQL file only do what the PR describes?
- [ ] Are there any unexpected `DROP TABLE` or `DROP COLUMN` statements?
- [ ] Do new fields have reasonable defaults?
- [ ] Do foreign keys have the correct `ON DELETE` behavior? (cascade vs set null)
- [ ] Were indexes added for columns that will be frequently filtered/searched?
- [ ] Does the TypeScript schema match the generated SQL?
